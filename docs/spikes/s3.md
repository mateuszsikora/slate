# S-3 — Flash budget

**Verdict: pass, with room to spare.** A skeleton linking everything design.md §6.1
commits to builds to **1 409 680 B (1.34 MiB)** and occupies **44.8 % of a 3 MB OTA
partition**. The image was flashed to the board and runs without a reset.

The pass criterion in §13 is met. It is also, as of this spike, no longer the binding
constraint — see [Board variant](#board-variant).

Measured 2026-08-06 against issue #3.

## Board variant

The premise of design.md §6.3 — "The N8R8 variant has 8 MB of flash" — does not hold for
the hardware in hand. Read out of the silicon rather than off the silkscreen or the
vendor page:

```
$ esptool.py --port /dev/cu.usbmodem* flash_id
Chip is ESP32-S3 (QFN56) (revision v0.2)
Features: WiFi, BLE, Embedded PSRAM 8MB (AP_3v3)
Manufacturer: 46
Device: 4018
Detected flash size: 16MB
Flash type set in eFuse: quad (4 data lines)
```

Confirmed twice, once with `--no-stub` and once with the stub loader. JEDEC device ID
`0x4018` — the `0x18` capacity byte is 2^24 bytes, so the size comes from the flash chip
itself. The module is **ESP32-S3-WROOM-1-N16R8**, 16 MB flash and 8 MB octal PSRAM.

Maintainer's decision, recorded on #5: **target 16 MB.** Fitting an 8 MB board is welcome
if it happens but is not a goal. Every figure below is therefore reported against both a
3 MB and a 6 MB partition. Amending §6.3 and §13 belongs to #5, which owns the board
variant decision.

## Decisions this spike was asked to settle

### Glyph count and character coverage

**83 icons**, listed by name in `tools/fonts/icons.txt`. §8 budgets 60–80, so this is
three over. Accepted by the maintainer rather than trimmed to hit the range: at 44.8 %
occupancy the difference is noise, and every icon on the list is reachable from a
component in §7 or from a state one of them must render. The list is committed, so the
selection can be argued with and the measurement reproduced.

Coverage is Latin-1 plus the Polish letters outside it. Wider scripts remain deferred
per §8.

### Font count — a contradiction in the design document

§13 specifies "two fonts and the icon set". §8 requires **three** type steps (hero 44,
body 20, caption 15), and §7.1 separately requires a "large icon" on the 2×2 light tile,
which means two icon sizes because a scaled icon font looks poor.

These cannot both be satisfied. Resolved in favour of §8 and §7.1, which describe what
actually reaches the screen; measuring two fonts would have understated the image.
Accepted by the maintainer. **§13's "two fonts" should be corrected** when §6.3 is
amended under #5.

## What this number does not include

The measurement is a **lower bound**, and quoting it as "the size of Slate" would be
wrong.

- This is a skeleton. The M1–M3 feature code — UI runtime, component library, Home
  Assistant client, configuration parser — is not written yet and adds to it. With
  4.66 MiB free on a 6 MB partition this is not a risk, but the figure will grow.
- The editor bundle (§10, target under 400 KB gzipped) lives in LittleFS, not in the app
  partition. It does not compete with this budget, but it does constrain the partition
  table in #5.
- Pin assignments are placeholders. The panel, GT911 and CH422G code is **linked and
  counted but never executed** — its size is known, its correctness is not. Bring-up is
  #6, and nothing has yet been drawn on the screen.

## Method

**The measurement skeleton is not in the repository.** It was an instrument, it has done
its job, and keeping it would have been actively harmful: `firmware/main/slate_main.c`
contained a `volatile` guard whose only purpose was to force dead code past the linker,
`-1` placeholder pins, and a bring-up path compiled specifically so that it would never
run. Whoever starts M1 should write `firmware/` deliberately, not inherit a rig. The
configuration underneath it — the part that was verified rather than faked — is preserved
in the [appendix](#appendix-configuration-that-m1-should-not-have-to-rediscover).

What the skeleton was: an ESP-IDF project whose `app_main` called into every subsystem
design.md §6.1 commits to, so the linker kept all of it. Roughly 470 lines. It built,
flashed, and ran on the board. Rebuilding it from the appendix is a couple of hours.

Two details of the rig that matter for reading the numbers above:

- The partition table used for measuring deliberately oversized the app partition to
  6 MB, so that an image exceeding 3 MB would still link and be measurable instead of
  failing the build with "app partition is too small" and hiding by how much. It was
  never a candidate for the real table — that is #5.
- Fonts were generated by `tools/fonts/generate.sh`, which **is** committed, along with
  the glyph list in `tools/fonts/icons.txt`. The generated `.c` sources are not: ~1.1 MB
  of hex per revision, unreviewable, and re-entering git history on every glyph-list
  change. Upstream typeface versions are pinned in the script, so regenerating reproduces
  the font figures exactly.

Toolchain: ESP-IDF **v5.5.5**, `xtensa-esp-elf-gcc` 14.2.0, esptool 4.12.0.

### The measurement rule, and how it was broken

Every subsystem has to be *called*, not merely included: a header referenced by nothing
contributes nothing to the image, and a budget measured that way is fiction.

This file's first version violated its own rule. `esp_https_ota` was guarded by
`if (0) { ... }` to keep it linked without running it — and GCC, able to prove the branch
dead, removed it. The entire release-OTA path was absent from the measured image:

```
$ xtensa-esp32s3-elf-nm build/slate.elf | grep " T esp_https_ota"
(nothing)
```

Restoring it added **94 816 B**, 7 % of the image, that would otherwise have gone
unreported. The fix is a `static volatile bool` guard, which the compiler cannot fold
away. All twelve subsystems are now verified present with `nm` rather than assumed.

The same class of error nearly produced two more bad numbers. The first attempt at the
`-Og` and full-bundle variants reported sizes *identical* to the release build, because
`SDKCONFIG_DEFAULTS` is only consulted when no `sdkconfig` exists — both "variants"
silently rebuilt the same configuration. Every variant above is now built with an
explicit `-DSDKCONFIG` and its resulting configuration is grepped for the setting it was
supposed to change.

### A trap in `idf.py size-components`

The tool attributes **89 302 B of `.rodata` to `libesp_app_format.a`**, 8 % of the image.
It is not there. From the map file:

```
.rodata.__esp_system_init_fn_init_show_app_info.str1.1
              0x3c0d0120    0x15ce9   libesp_app_format.a(esp_app_desc.c.obj)
                               0xdf   (size before relaxing)
```

That object's own contribution is `0xdf` — **223 bytes**. The remaining 89 KB is the
merged string-literal pool for the whole image; the linker attributes a pooled `.str1.1`
section to the first object contributing to it, and the size tool repeats the
attribution. Anyone reading a per-component breakdown of this project will hit the same
thing.

## Findings for other issues

**#7 — CH422G forces the legacy I2C driver.** There is no `espressif/esp_io_expander_ch422g`
component; the registry returns 404. CH422G lives in `espressif/esp32_io_expander` 1.1.1,
whose C API takes a legacy `i2c_port_t` rather than an `i2c_master_bus_handle_t`. Since
GT911 and the expander share one bus, the whole bus must use one stack. Mixing them is
not merely untidy — ESP-IDF detects it and aborts:

```
E i2c: CONFLICT! driver_ng is not allowed to be used with this old driver
abort() was called at PC 0x420566a0 on core 0
```

which held the skeleton in a boot loop until it was fixed. Either keep the legacy stack
or write a CH422G driver against the new one. Using only the legacy stack also saved
5 952 B versus linking both.

**#6 / M1 — LVGL needs a bigger stack than app_main gets.** LVGL init plus widget
creation overflows the 3.5 KB default main task stack, caught as
`vApplicationStackOverflowHook`. Raised to 8192 B here; the real firmware should run LVGL
on its own task per §6.1.

**M1 — `lv_color_t` is not the render format.** In LVGL 9 `lv_color_t` is a 24-bit struct
regardless of render depth, so sizing an RGB565 draw buffer as `lv_color_t[]`
over-allocates by 50 %. This cost 38 400 B of DIRAM in the first build and pushed
occupancy to 88 %. Size draw buffers in bytes from the colour format.

## Hardware verification

`docs/agent-workflow.md` §5 forbids calling firmware verified from a successful compile.
The release image was flashed over the `UART` port and observed:

```
I (871) app_init: Project name:     slate
I (1011) main_task: Calling app_main()
I (1011) slate: slate flash-budget skeleton (spike S-3)
W (1161) slate: panel/touch bring-up linked but not run (placeholder pins)
I (1041) wifi:wifi firmware version: b9f67df
```

**Zero reboots and zero panics across 40 seconds** of serial capture, after two earlier
boot loops were diagnosed and fixed. Bootloader confirms the partition table and
`SPI Flash Size : 16MB`; PSRAM enumerates as 8 MB octal at 80 MHz.

What was *not* verified: anything the panel does. The display was never driven — the pins
are placeholders and the bring-up path is deliberately not executed.

### Serial access


The board exposes two USB-C ports. The one that enumerates is **`UART`** — a WCH CH343
bridge, VID `0x1a86` / PID `0x55d3`, appearing on macOS as `/dev/cu.usbmodem*` with no
driver install. The native ESP32-S3 USB port (VID `0x303a`) did not enumerate. The bridge
is unreliable above the default baud rate: two attempts to back up the factory flash
failed with `Invalid head of packet` immediately after the baud change, so the Waveshare
demo image was overwritten without a backup. It remains available from the vendor wiki.

## Appendix: configuration that M1 should not have to rediscover

The measurement skeleton is not committed — it was an instrument, and it contained
deliberate fakery that must never reach real firmware (a `volatile` guard forcing dead
code to link, `-1` placeholder pins, a bring-up path compiled but never executed). What
is worth keeping is the configuration underneath it, every line of which was verified by
booting the image on the board rather than copied from a tutorial.

ESP-IDF **v5.5.5**, `xtensa-esp-elf-gcc` 14.2.0, esptool 4.12.0.

```
CONFIG_IDF_TARGET="esp32s3"

# ESP32-S3-WROOM-1-N16R8: 16 MB quad flash, 8 MB octal PSRAM.
CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
CONFIG_ESPTOOLPY_FLASHFREQ_80M=y
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_OCT=y
CONFIG_SPIRAM_SPEED_80M=y
CONFIG_SPIRAM_FETCH_INSTRUCTIONS=y
CONFIG_SPIRAM_RODATA=y
CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y

# The shipped image is built -Os; the -Og overlay is 9.8 % larger.
CONFIG_COMPILER_OPTIMIZATION_SIZE=y

# design.md §11.2 — rollback links the ota_ops verification path in.
CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y

# design.md §11.3 — see #14: without a coredump partition every panic
# logs "Core dump flash config is corrupted!" and then falsely reports success.
CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH=y
CONFIG_ESP_COREDUMP_DATA_FORMAT_ELF=y

# design.md §11.4 — no HTTPS on the device, but esp_https_ota links mbedTLS
# regardless. Common roots cost 17 924 B; the full bundle costs 68 983 B.
CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y
CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_DEFAULT_CMN=y

CONFIG_HTTPD_MAX_REQ_HDR_LEN=1024
CONFIG_HTTPD_WS_SUPPORT=y

# LVGL init plus widget creation overflows the 3.5 KB default. See #6 —
# the real firmware should run LVGL on its own task per §6.1.
CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192

CONFIG_LV_COLOR_DEPTH_16=y
```
