# S-4 — Home Assistant registry permissions

**Verdict: the area-aware entity picker is a primary feature, not a degraded one.** A
non-admin long-lived token reads `config/entity_registry/list` and
`config/area_registry/list` in full — byte-for-byte the same payload an administrator
gets. So does a token from the read-only group.

Measured 2026-08-06 against issue #4.

Section numbers here are DESIGN.md's current ones, and two things moved after this was
measured. The Home Assistant chapter became §§5.5–5.8 when providers were made neutral
(#77), and the optimistic-update rule quoted from it is now §5.3. `GET /entities` became
the provider-neutral `GET /resources`, so the §4.1 field list this document measures
against is one §4.1 no longer carries. The corrections asked for below have since landed,
so where §5.7 and §12 are quoted it is as they read on the day.

DESIGN.md §5.7 stated that these "require an administrator account". That is not merely
out of date: neither command has ever carried an admin requirement in any Home Assistant
release checked, back to December 2020. §5.7 needs correcting — see
[What this changes](#what-this-changes).

The degraded path §5.7 mandates still has to be built, but for a different reason than
the one written down, and it is not an error path. See
[The degraded path is not dead code](#the-degraded-path-is-not-dead-code).

## Setup

| | |
|---|---|
| Home Assistant | 2026.7.4, the maintainer's live instance, plain HTTP on the LAN |
| Transport | WebSocket API, `/api/websocket` — §5.5's transport, not REST |
| Scale | 1 045 registry entries, 590 states, 113 devices, 6 areas |
| Privilege levels | `system-admin` (control), `system-users`, `system-read-only` |
| Instrument | not in the tree — see [Reproducing](#reproducing) |

Both non-admin accounts were created for this spike and **deleted afterwards**; the
instance is back to the five accounts it started with, and both long-lived tokens were
confirmed dead (`auth_invalid`) after deletion. The one entity that was written to was a
throwaway `input_boolean` created and deleted by the spike. Nothing in the house was
toggled.

REST was deliberately not tested. Firmware talks WebSocket per §5.5, the two do not share
an authorisation path, and a green result from the wrong protocol would have been a
confident wrong answer.

### The instrument check

A spike whose answer is "the restriction isn't there" is one misconfiguration away from
being worthless — an accidentally-admin token would produce exactly this table. Three
independent facts say the tokens were what they claimed:

- `auth/current_user` returns `is_admin: false, is_owner: false` for both.
- `config/auth/list` — an admin-only command — returns `unauthorized` for both, on the
  same connection, seconds after the registry call succeeded.
- The read-only token is refused `call_service`, which a non-admin token is granted. Two
  distinct non-admin levels behaving differently rules out "both tokens were secretly the
  same account".

## The design document is wrong, and was never right

Not a version drift. Read out of the Home Assistant source, checking whether
`config/entity_registry/list` carries the `@require_admin` decorator:

| Release | `entity_registry/list` admin-gated |
|---|---|
| 2020.12.0 | no |
| 2021.12.0 | no |
| 2022.1.7 | no |
| 2023.1.0 | no |
| 2025.1.0 | no |
| 2026.7.4 | no |

In 2026.7.4 the decorator appears twice in `homeassistant/components/config/entity_registry.py`
— on `update` and `remove` — and four times in `area_registry.py`, on `create`, `update`,
`delete` and `reorder`. Every mutating command is admin-only. Every `list` command is not.

This is the shape one would expect in hindsight: the registries describe how the
installation is organised, which every user's own frontend needs in order to render
anything at all.

## What this changes

§5.7 read, on the day this was measured:

> `GET /entities` requires the registries: `config/entity_registry/list` and
> `config/area_registry/list`. These require an administrator account. If the token lacks
> the privilege, the picker degrades to a flat list derived from `subscribe_entities`
> with no area grouping.

Two corrections, neither of which this PR makes — the spike records, it does not rewrite
the design document (same convention S-3 followed for §6.3, which was corrected under the
issue that owned it). Both are carried by **#48**:

1. **"These require an administrator account" is false.** A non-admin token is enough.
2. **The degradation trigger is wrong.** It is not privilege. It is any failure of the
   command — an older or unusual instance, a transport error, a future Home Assistant
   that tightens this. Firmware should degrade on *failure*, not on a permission it
   predicted in advance.

The useful half of §5.7 survives intact: the degraded path "must be implemented, not
assumed away" is still correct, and more so than the sentence before it suggests.

§12's recommendation of "a dedicated account with limited privileges" also needs a
qualifier — see [Which account to recommend](#which-account-to-recommend).

## The degraded path is not dead code

The interesting number is not in the permission table. On this instance:

| | count | share |
|---|---:|---:|
| Registry entries with an area resolvable | 387 | 37 % |
| Registry entries with **no** area at all | 658 | 63 % |

Per domain, counting only entities that actually have state:

| Domain | with state | area-resolvable |
|---|---:|---:|
| `light` | 35 | 24 |
| `sensor` | 226 | 74 |
| `switch` | 52 | 31 |
| `binary_sensor` | 82 | 55 |

So even with complete registry access, **most entities cannot be grouped by area**. The
"flat list, no area grouping" presentation §5.7 describes as the degraded mode is what the
picker shows for the majority of a real instance's entities regardless of permissions. It
is a first-class UI state, not an error banner — and the editor (#32) has to make it look
deliberate rather than broken.

## Data shape for `GET /entities`

§4.1 promises `entity_id`, `friendly_name`, `domain`, `area`, `state` and
`supported_features`. Where each actually comes from, measured rather than assumed:

| Field | Source | Note |
|---|---|---|
| `entity_id` | either registry or `get_states` | — |
| `domain` | derived, prefix of `entity_id` | not a field anywhere |
| `state` | `get_states` only | absent from the registry |
| `supported_features` | `get_states` attributes only | present on 86 of 590 states |
| `friendly_name` | `get_states` attributes | present on **590 of 590** |
| `area` | entity → **device** → area | see below |

**`friendly_name` cannot come from the registry.** The registry's `name` field is set on
5 entries out of 1 045; `original_name` covers 959, and 81 have neither. Home Assistant
composes the displayed name from the device name plus the entity name when
`has_entity_name` is true (456 entries here), and the frontend does that composition. The
already-composed string arrives free in the state attributes, on every entity. Firmware
should not reimplement the composition.

**No entity on this instance has `area_id` set directly — zero out of 1 045.** All 387
area assignments come from the entity's device. A `GET /entities` that reads only
`config/entity_registry/list` returns an empty `area` for every entity and looks like a
bug. The join is mandatory:

```
entity_registry.area_id
  ?? device_registry[entity.device_id].area_id
  → area_registry[area_id].name
```

Whether other installations assign areas per entity is unknown; the field exists, so the
first branch stays. But the device branch is the one that produces every result here.

### Payload sizes

Measured on the wire, single frames, this instance:

| Command | Bytes | Entries |
|---|---:|---:|
| `config/entity_registry/list` | 635 087 | 1 045 |
| `config/entity_registry/list_for_display` | **83 809** | 586 |
| `get_states` | 276 909 | 590 |
| `config/device_registry/list` | 77 142 | 113 |
| `config/area_registry/list` | 1 270 | 6 |

`list_for_display` is the frontend's own picker payload: short keys (`ei`, `di`, `en`,
`hn`, `ec`), and pre-filtered — 586 entries against the full registry's 1 045. The 459 it
drops are exactly the disabled ones, which have no state and cannot be put on a tile.
Hidden entities are kept, flagged with `hb` (7 here), so hiding remains the picker's
decision rather than the transport's. It is **7.6× smaller** and closer to what the picker
wants.

For an ESP32 that means the area-aware picker costs:

| Approach | Bytes to receive and parse |
|---|---:|
| `entity_registry/list` + devices + areas + `get_states` | 990 408 |
| `list_for_display` + devices + areas + `get_states` | **439 130** |

A 56 % saving for a one-line change of command. Both figures are large enough that
`GET /entities` cannot hold the whole thing as a cJSON DOM in internal RAM — the 277 KB
`get_states` frame alone expands several-fold when parsed. This lands in PSRAM or is
consumed incrementally; §5.7's "cached in RAM, not NVS" stands, but the RAM in question
is PSRAM. Home Assistant does not paginate these commands, so the frame size is not
negotiable.

`device_registry/list` at 77 KB is heavy for what firmware takes from it — an
`id → area_id` map of 113 entries. There is no compact variant.

## Error codes firmware has to match on

Not interchangeable, and the difference is not documented anywhere upstream:

| Situation | Frame |
|---|---|
| Bad or revoked token | `{"type": "auth_invalid", "message": "Invalid access token or password"}` |
| Admin-only command, non-admin token | `{"success": false, "error": {"code": "unauthorized", "message": "Unauthorized"}}` |
| **`call_service` refused to a read-only token** | `{"success": false, "error": {"code": "home_assistant_error", "message": "Unauthorized"}}` |

The third is the trap. A denied service call does **not** come back as `unauthorized`; it
arrives as the generic `home_assistant_error` with the word "Unauthorized" only in the
human-readable message. Firmware that switches on `error.code` will classify a permission
problem as a transient Home Assistant fault and, per §5.3, revert the optimistic update
after 3 s and show a generic error — every single time, forever, with no hint that the
token is the cause. Matching this needs the message, not the code.

Authentication failure is also structurally different from command failure: `auth_invalid`
is a top-level frame type with no `id`, arriving before any command is sent, and Home
Assistant closes the socket afterwards. It must not be routed through the same handler as
a failed command result.

### The degraded path's payload

`subscribe_entities` (§5.6) delivers the compressed form, and it is the source of the
flat-list fallback:

```json
{"id": 1, "type": "event", "event": {"a": {
  "light.shelly_25_living_room_1_switch_0": {
    "s": "off",
    "a": {"supported_color_modes": ["onoff"], "color_mode": null,
          "friendly_name": "shelly-25-living-room-1 Output 0", "supported_features": 0},
    "c": "01KZ9SNPW3HZEDY4RPDVRY1SRR", "lc": 1785961569.1556518}}}}
```

`s` is the state, `a` the attributes, `c` the context id, `lc` last-changed. Of §4.1's six
fields the fallback yields five — `entity_id`, `friendly_name`, `state`,
`supported_features` and a derivable `domain`. Only `area` is lost, which is precisely
what §5.7 says. That sentence is correct and the measurement confirms it.

## Which account to recommend

§12 recommends "a dedicated restricted account" for the Home Assistant token. This spike
narrows what that can mean, because Home Assistant's three groups are not interchangeable:

| Group | Reads registries | Calls services | Usable for Slate |
|---|---|---|---|
| `system-admin` | yes | yes | yes, but more privilege than needed |
| `system-users` | yes | yes | **yes — this is the recommendation** |
| `system-read-only` | yes | **no** | no: every tap fails |

`system-users` is the answer: it reads everything the picker needs and calls services,
while being refused registry writes and all account administration. A read-only account
would produce a dashboard that renders perfectly and does nothing — and, because of the
error-code trap above, would explain itself as a Home Assistant fault.

Worth stating plainly in the eventual documentation, since "restricted" reads like
"read-only" to anyone skimming.

Creating such an account is fully scriptable — user, password and long-lived token,
without touching the frontend. The script is in [Reproducing](#reproducing), and
first-run documentation (#38) can lift it.

## What this does not prove

- **One instance, one version.** 2026.7.4, 1 045 entities, 6 areas, a mix of MQTT, Shelly
  and template entities. The permission answer is read from the upstream source as well as
  measured, so it generalises; the *shape* numbers — 0 direct `area_id`, 63 % area-less,
  5 registry names — are properties of this installation and another one will differ.
- **No proxy, no HTTPS, no Nabu Casa.** Plain HTTP on the LAN, which is what §12 assumes.
  An instance behind an authenticating proxy may fail earlier, on the transport.
- **Long-lived tokens only.** The token was minted through the same auth flow the frontend
  uses. A token issued by a different flow was not tested; there is no reason to expect a
  difference, as authorisation is attached to the user, not to the token.
- **`floor`, `label` and `category` registries returned empty** — permitted, but with
  nothing in them. They are not in §4.1 and were probed only to check the permission
  boundary; if floors ever matter to the picker, their contents are still unmeasured.
- **Nothing here was run on the panel.** This is a protocol and permission measurement
  made from a laptop. The ESP32 has not spoken to Home Assistant yet — that is #16.

## Findings for other issues

- **#30 (`GET /entities` and `GET /areas`) — three things.** Use
  `entity_registry/list_for_display`, not `list`: 83 KB against 635 KB and already
  filtered to entities that can hold a tile. Join through `device_registry` for `area`, or
  every `area` in the response is null. Take `friendly_name` and `supported_features` from
  `get_states`, not from the registry. The degraded fallback triggers on command failure,
  not on a permission check.
- **#16 (HA WebSocket client) — the error taxonomy above.** `auth_invalid` is a
  pre-command frame that closes the socket; `unauthorized` and `home_assistant_error` are
  command results and mean different things. The reconnect logic in §5.5 must not retry an
  `auth_invalid` with backoff forever — a revoked token is not a transient fault and needs
  the error mode screen (§6.5), not a retry loop.
- **#18 (service calls) — a denied call is indistinguishable by code.** Match
  `home_assistant_error` with message `Unauthorized` if the pending-state revert (§5.3) is
  to say anything useful.
- **#38 / first-run documentation — recommend `system-users` explicitly**, and say that a
  read-only account does not work. The account-creation script here can be lifted.
- **#48 corrects §5.7 and §12.** Deliberately not done in this PR: the spike records the
  finding, the design document edit belongs to its own issue — the convention S-3 set when
  it left §6.3 to #5.

## Reproducing

**The instrument is not in the tree**, following S-1 and S-3 — it is 150 lines of Python
against an external service, not firmware, and a copy in `tools/` would rot. It is
reproduced here in full instead, which is cheaper than a repository path for something
this size.

Requires `pip install websockets` and an admin long-lived token in `HA_TOKEN`.

### 1. Create a non-admin account and mint its token

A long-lived token can only be minted from inside the target user's own session, so this
creates the user with the admin token and then logs in as that user exactly as the
frontend does.

```python
import asyncio, json, os, secrets, sys, urllib.parse, urllib.request, websockets

URL = os.environ.get("HA_URL", "http://homeassistant.local:8123")
WS_URL = URL.replace("http://", "ws://") + "/api/websocket"
ADMIN_TOKEN, CLIENT_ID = os.environ["HA_TOKEN"], URL + "/"

def post(path, payload):
    req = urllib.request.Request(URL + path, data=json.dumps(payload).encode(),
                                 headers={"Content-Type": "application/json"}, method="POST")
    with urllib.request.urlopen(req, timeout=10) as r:
        return json.loads(r.read())

async def ws_command(token, *commands):
    out = []
    async with websockets.connect(WS_URL, max_size=None) as ws:
        await ws.recv()
        await ws.send(json.dumps({"type": "auth", "access_token": token}))
        if json.loads(await ws.recv()).get("type") != "auth_ok":
            raise SystemExit("auth failed")
        for i, cmd in enumerate(commands, 1):
            await ws.send(json.dumps({"id": i, **cmd}))
            while True:
                frame = json.loads(await ws.recv())
                if frame.get("id") == i and frame.get("type") == "result":
                    break
            if not frame.get("success"):
                raise SystemExit(f"{cmd['type']}: {frame.get('error')}")
            out.append(frame["result"])
    return out

async def main(username, group):          # group: system-users | system-read-only
    password = secrets.token_urlsafe(18)
    (user,) = await ws_command(ADMIN_TOKEN, {"type": "config/auth/create", "name": username,
                                             "group_ids": [group], "local_only": False})
    user_id = user["user"]["id"]
    await ws_command(ADMIN_TOKEN, {"type": "config/auth_provider/homeassistant/create",
                                   "user_id": user_id, "username": username, "password": password})
    flow = post("/auth/login_flow", {"client_id": CLIENT_ID, "handler": ["homeassistant", None],
                                     "redirect_uri": CLIENT_ID})
    step = post(f"/auth/login_flow/{flow['flow_id']}", {"client_id": CLIENT_ID,
                                                        "username": username, "password": password})
    req = urllib.request.Request(URL + "/auth/token", method="POST", data=urllib.parse.urlencode(
        {"grant_type": "authorization_code", "code": step["result"], "client_id": CLIENT_ID}).encode())
    with urllib.request.urlopen(req, timeout=10) as r:
        session_token = json.loads(r.read())["access_token"]
    (llat,) = await ws_command(session_token, {"type": "auth/long_lived_access_token",
                                               "client_name": username, "lifespan": 30})
    print(json.dumps({"user_id": user_id, "password": password, "token": llat}, indent=2))

asyncio.run(main(sys.argv[1], sys.argv[2]))
```

Delete afterwards with `{"type": "config/auth/delete", "user_id": ...}` using the admin
token; the user's long-lived tokens die with the account.

### 2. Probe

Run once per token, with `HA_TOKEN` set to that token. Every frame is written verbatim so
the results can be diffed between privilege levels rather than eyeballed.

```python
COMMANDS = {
    "auth_current_user":  {"type": "auth/current_user"},
    "entity_registry":    {"type": "config/entity_registry/list"},
    "list_for_display":   {"type": "config/entity_registry/list_for_display"},
    "area_registry":      {"type": "config/area_registry/list"},
    "device_registry":    {"type": "config/device_registry/list"},
    "get_states":         {"type": "get_states"},
    "auth_list":          {"type": "config/auth/list"},   # admin-only: the control
}
```

sent over the same authenticated connection as `{"id": n, **cmd}`, reading frames until
one arrives with a matching `id` and `type: "result"`. Success is `frame["success"]`;
denial carries `frame["error"]["code"]`.

The write side — `call_service` against a throwaway `input_boolean` created with
`{"type": "input_boolean/create", "name": "..."}` and deleted with
`{"type": "input_boolean/delete", "input_boolean_id": ...}`, plus `subscribe_entities` and
an attempted `config/entity_registry/update` — follows the same pattern.

Comparing privilege levels is then a hash over the canonicalised results:

```python
hashlib.sha256(json.dumps(result, sort_keys=True).encode()).hexdigest()[:12]
```

which is what produced the identical-payload table above.
