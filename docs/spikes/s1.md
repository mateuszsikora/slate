# S-1 — Rebuild idempotency

**Verdict: PASS.** Over 500 build/destroy cycles the free LVGL heap did not move by a
single byte. Criterion (design.md §13) was 1 % with no downward trend; measured drift
was 0 B (0.0000 %) with a fitted slope of 0.0000 B/cycle.

The runtime architecture in ADR-1 and §6.4 stands. Nothing needs rethinking before M1.

## Setup

| | |
|---|---|
| Board | ESP32-S3-WROOM-1-N16R8, chip rev v0.2 (as read out in #3) |
| ESP-IDF | v5.5.5 |
| LVGL | 9.5.0, built-in allocator (`LV_USE_BUILTIN_MALLOC`) |
| LVGL heap | 2 MB (2,097,152 B) in PSRAM at `0x3c090998`, per §6.2 |
| Cycles | 10 warmup + 500 measured |
| Wall time | 59 s |
| Source | `spikes/s1-rebuild-idempotency/` |

Each cycle generates a §3.3-shaped JSON config, parses it with cJSON, builds the widget
tree onto the §3.2 grid, renders it, deletes it, and samples `lv_mem_monitor()`.

Three things about the method are worth stating, because each is a way this spike could
have produced a meaningless green result:

- **The tree varies between cycles** — 3 to 10 tiles, different types, labels and
  placement, driven by a cycle-seeded PRNG. Rebuilding an identical tree 500 times lets
  the allocator hand back the same blocks in the same order and hides a leak behind
  reuse. §6.4's real case is `PUT /config` with a *different* config.
- **The tiles are semantic components** (ADR-2), not empty containers — light, cover,
  sensor, scene, plus the §3.1 unknown-type placeholder. What actually leaks in LVGL is
  local styles, label text buffers and running animations, so the components create all
  three. Marquee labels (§7.5 text overflow) and pending-state pulses (§7.5) are in
  deliberately: deleting an object with a live animation attached is the classic LVGL
  leak, and a spike that skipped it would be measuring the easy half.
- **The standing tree is sampled too**, not just the post-destroy state. A run in which
  the build silently did nothing would give a flawlessly flat series. The built-vs-after
  gap is the evidence that each cycle allocated something to begin with.

## Result

| Metric | Value |
|---|---|
| Free LVGL heap, cycle 1 | 2,088,632 B |
| Free LVGL heap, cycle 500 | 2,088,632 B |
| **Drift** | **0 B (0.0000 %)** |
| Min / max across the run | 2,088,632 / 2,088,632 B |
| **Trend (least-squares)** | **+0.0000 B/cycle** |
| Live allocation count, after destroy | 97, constant across all 500 cycles |
| Fragmentation | 1 %, constant |
| Peak tree cost | 2,468 – 12,212 B (3 – 10 tiles) |
| Peak LVGL heap ever used | 18,500 B |
| ESP internal heap free | 294,631 B, constant |
| ESP PSRAM heap free | 6,289,000 B, constant |

Not "within 1 %" — bit-identical. Free size, allocation count and fragmentation are the
same integer at cycle 500 as at cycle 1. Two separate flash-and-run rounds produced the
same numbers.

The one-time step is visible and accounted for: before any tree exists the heap has
2,088,692 B free across 96 allocations; from the first cycle onward it settles at
2,088,632 B across 97. That is a single 60-byte allocation LVGL makes on first render
and keeps — a lazily-initialised cache, not a leak. It is why the baseline is taken
after 10 warmup cycles; charging a one-time step to the trend would misreport a healthy
runtime. The pre-warmup number is published here so the step stays visible rather than
hidden by the warmup.

## Negative control

A run that reports zero drift says as much about the instrument as about the runtime, so
the harness was checked against a leak that is known to be there. Building with
`idf.py -DS1_LEAK_BYTES=64 build` leaks 64 B of LVGL heap per tile per cycle and changes
nothing else:

| Metric | Clean | Leaking (64 B/tile) |
|---|---|---|
| Free heap, first → last | 2,088,632 → 2,088,632 | 2,083,656 → 1,877,192 |
| Drift | 0 B (0.0000 %) | **−206,464 B (−9.9087 %)** |
| Trend | +0.0000 B/cycle | **−414.14 B/cycle** |
| Live allocations, first → last | 97 → 97 | 167 → 3,101 |
| Fragmentation | 1 % → 1 % | 1 % → 3 % |
| Verdict | PASS | **FAIL** |

The arithmetic checks out, which is the point: 2,939 tiles were built across the run, so
206,464 B of drift is 70.25 B per 64-byte request — the extra 6.25 B is TLSF block header
and alignment. The harness sees a leak of this size clearly, and the clean run's zero is
therefore a measurement rather than a blind spot.

**The control also exposed something that matters beyond this spike:** during the leaking
run the ESP heap never moved. PSRAM free stayed at 6,289,000 B from first cycle to last,
because the leak lives inside LVGL's pre-allocated 2 MB pool and never reaches the ESP
allocator. A `GET /status` that reports only `free_heap` (§4.1) would show a perfectly
healthy device while the UI heap bled out. Whatever ships for §4.1 should surface the
LVGL heap separately.

## What this does not prove

- **No display pipeline.** This is a dummy display: no RGB panel, no GT911, no CH422G.
  Those are #6 and #7. Rendering was left switched on so draw-time allocations are
  counted, but the framebuffer and panel driver are not in the measurement.
- **No real fonts or icons.** Built-in Montserrat stands in for the §8 type scale so this
  spike does not depend on the unmerged asset pipeline in #3. Glyph data is `const` and
  never allocated at runtime, so the substitution cannot move a heap number — but the
  glyph *cache* behaviour of a bpp:4 icon font is untested here.
- **500 cycles, not 5,000.** §13 asked for 500. A defect with a period longer than that
  would not show up. Fragmentation held flat at 1 %, which is the signal that would most
  likely have moved first, so there is no reason to suspect one.
- **No entity churn.** The subscription/state-store path (§5.2) is not exercised; this is
  the tree lifecycle only.

## Findings for other issues

- **The 2 MB LVGL heap budget in §6.2 is enormously overprovisioned.** A full page of 10
  tiles costs 12.2 KB; peak use across the whole run was 18.5 KB. That is roughly 1 % of
  the budget. The 2 MB does no harm on 8 MB of PSRAM and there is no reason to change it
  now, but anyone sizing memory in #5 or hitting PSRAM pressure later should know the
  widget tree is not where the memory goes.
- **Input for S-2 (#2).** ~1.2 KB of LVGL heap per tile, and a 10-tile page builds and
  renders well inside one cycle. S-2's 20-tile target is ~25 KB of tree — still nothing.
  Whatever limits tile count, it will be frame time, not heap.
- **For §4.1 `GET /status`.** Report the LVGL heap alongside `free_heap`. See the
  negative-control finding above.

## Reproducing

```bash
cd spikes/s1-rebuild-idempotency
idf.py build
idf.py -p /dev/cu.usbmodem* flash
idf.py -p /dev/cu.usbmodem* monitor | tee run.log     # ~60 s, ends with "S-1 complete"
python3 tools/s1_report.py run.log
```

The report script prints the table above and exits non-zero on failure. For the negative
control, build into a separate directory so the clean build is not clobbered:

```bash
idf.py -B build-leak -DS1_LEAK_BYTES=64 build
idf.py -B build-leak -p /dev/cu.usbmodem* flash
```

The config generator is seeded from the cycle number, so a given cycle builds the same
tree on every run and a failure can be re-run in isolation.
